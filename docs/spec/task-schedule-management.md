# ТЗ: Система управления расписанием CollegeLMS (эталонное)

> **Статус:** утверждено пользователем 2026-09-17.
> **Назначение:** эталонное техническое задание — источник требований для реализации «с нуля» и критерий оценки результатов работы AI-моделей.
> **Область:** домен расписания CollegeLMS — REST API, веб-приложение, бот Max, мини-приложение Max.
> **Правило:** требования этого документа — целевое состояние. Отсутствие функции в текущем коде не отменяет требование; отличие реализации от документа считается дефектом.

## 1. Назначение и область

### 1.1. Цель

Единое управление расписанием колледжа: диспетчер формирует расписание семестра, вносит корректировки (вручную или импортом XLSX), система применяет их транзакционно, рассылает уведомления группам и преподавателям в мессенджере Max и ведёт журнал изменений.

### 1.2. Входит в область

| Блок | Состав |
|------|--------|
| Расписание | просмотр (день, неделя, семестр, календарь), ручное редактирование диспетчером, метки изменений |
| Импорт/экспорт | полный импорт расписания на семестр из XLSX; экспорт дня/недели/семестра в PDF и XLSX |
| Корректировки | пакеты корректировок на день: импорт XLSX, ручное создание (снять/добавить/заменить/перенести), применение, уведомления, картинка в канал Max |
| Звонки | справочник времени пар, большая перемена, сокращённые пары |
| Нерабочие дни | управление праздниками и выходными, учёт в расписании и корректировках |
| Практики | УП/ПП: название, периоды, несколько преподавателей, дни УП с числом пар, импорт XLSX, слой поверх расписания |
| Вставки | специальные вставки в расписание (например, «Разговор о важном») |
| Изменения | вкладка изменений для пользователя в вебе, мини-приложении и боте |
| Журнал | журнал дат проведения пар для преподавателя |
| Бот Max | меню, роли, расписание, избранное, настройки уведомлений, диспетчерский режим |
| Мини-приложение Max | расписание, поиск, изменения, журнал, диспетчерский режим |

### 1.3. Вне области

- Аутентификация и управление пользователями (AuthService), справочники групп/преподавателей/студентов (LearningService) — используются как зависимости.
- Сайт колледжа, курсы, лекции, тесты, новости, обратная связь.
- Redis-кеширование домена расписания (Redis — только сессии).
- Другие каналы уведомлений, кроме бота Max (email, SMS, push — вне области).

### 1.4. Стек и ограничения

| Слой | Технологии |
|------|------------|
| Backend | .NET 10, ASP.NET Core Web API, EF Core (Npgsql), PostgreSQL 16 |
| Frontend | Next.js 14, TypeScript, Tailwind CSS 4, shadcn/ui |
| Бот | .NET 10, Max REST API, отдельная БД бота |
| Файлы | XLSX — ClosedXML, PDF — QuestPDF, изображения — ImageSharp, локальная ФС (`import/`) |
| Инфраструктура | Docker Compose, Nginx, GitHub Actions CD |

Обязательные конвенции проекта:

- `Result<T>` во всех сервисах; `ExceptionHandlerMiddleware` ловит неожиданные исключения; try-catch в контроллерах и сервисах запрещён.
- FluentValidation для DTO, сообщения об ошибках на русском языке.
- Swagger (XML-комментарии + `ProducesResponseType` + примеры) и Postman-коллекция — обязательны для каждого endpoint.
- EF Core: snake_case, GUID PK (`ValueGeneratedNever`), `HasMaxLength` для строк, enum-ы строками (`HasConversion<string>`), индексы в конфигурациях, CHECK-ограничения в `Data/DbConstraints.cs`.
- Все интерфейсы, метки и сообщения — на русском языке.
- Импорт XLSX ≤ 10 МБ; имя выгружаемого файла содержит таймстемп (см. FILE-3).

## 2. Роли и интерфейсы

| Роль | Веб-приложение | Мини-приложение Max | Бот Max |
|------|----------------|---------------------|---------|
| Студент | расписание своей группы, изменения, календарь | расписание, поиск, избранное, изменения | расписание (сегодня/неделя/дата), избранное, изменения, настройки уведомлений |
| Преподаватель | + расписание преподавателя, журнал дат проведения пар | + журнал | то же, что студент (по своему профилю) |
| Диспетчер | управление расписанием, корректировками, звонками, нерабочими днями, практиками, вставками, импорт/экспорт, журнал корректировок | диспетчерский режим (файл XLSX / вручную) | диспетчерский режим (визард корректировки, отправка XLSX в каналы) |
| Админ | все возможности диспетчера | все возможности диспетчера | все возможности диспетчера |

Правила доступа:

- `AUTH-1`, `AUTH-2`, `AUTH-3` применяются ко всем операциям.
- Чтение расписания доступно всем ролям; запись — только `Dispatcher` и `Admin`.
- Журнал преподавателя — только роль `Teacher` (свои данные); `Admin`/`Dispatcher` могут смотреть журнал по `teacherId`.
- Диспетчерский режим бота и мини-приложения — только после входа по паролю диспетчера или для роли `Dispatcher`/`Admin`.

## 3. Термины и соглашения

| Термин | Определение |
|--------|-------------|
| Пара | занятие с номером 1–8, временем из справочника звонков, предметом, преподавателем, аудиторией |
| Неделя | учебная неделя семестра, нумерация с 1; `Week = 1` — первая неделя семестра |
| Семестр | период обучения; начало и количество недель — конфигурация (`Semester:StartDate`, `Semester:TotalWeeks`) |
| Пакет корректировки | сущность `CorrectionBatch` — корректировка расписания на одну дату; статусы: «Подготовлен» / «Применён» (подготовленный пакет можно удалить) |
| Позиция (строка) корректировки | `CorrectionPosition` — одно изменение внутри пакета (тип, группа, пара, предмет, преподаватель, примечание) |
| «сам.р.» | примечание при снятии пары: пара не удаляется из БД, студенты на неё не приходят, в интерфейсе — бейдж «Сам.р.» |
| «вм.X» | примечание при переносе: автоматически выставляется номер старой пары (X) |
| Бейджи изменений | «Добавлено», «Снято», «Замена», «Перенос» — метки пар, изменённых корректировкой |
| Вставка | специальное мероприятие в расписании (например, «Разговор о важном»), не занимает номер пары |
| Практика | период учебной (УП) или производственной (ПП) практики группы: название, один или несколько преподавателей |
| Нерабочая дата | выходной или праздник, отмеченный диспетчером; расписание и корректировки на дату не действуют |
| Затронутая группа/преподаватель | группа/преподаватель, упомянутые в позициях применённого пакета |

## 4. Модель данных

### 4.1. Существующие сущности (целевые поля)

| Сущность | Ключевые поля | Ограничения |
|----------|---------------|-------------|
| `ScheduleEntry` | `GroupId`, `TeacherId?`, `Subject`, `Room`, `DayOfWeek`, `NumberPair` (1–8), `Weeks: int[]`, `StartTime`, `EndTime`, `LessonType` | `NumberPair` 1–8, `StartTime < EndTime`, индекс по `GroupId`/`TeacherId`/`DayOfWeek`+`NumberPair` |
| `ScheduleHistory` | `ChangeType` (Add/Remove/Replace/Move), `AppliedAt`, `AppliedByUserId`, `GroupId`, `TeacherId?`, `Subject`, `Room?`, `DayOfWeek`, `NumberPair`, `Week`, `Note?`, `RemovedSubject?`, `RemovedTeacherId?`, `RemovedNumberPair?` | фиксирует каждое применённое изменение |
| `CorrectionBatch` | `CorrectionDate`, `Week`, `DayOfWeek`, `Status`, `CreatedByUserId?`, `AppliedByUserId?`, `AppliedAt?` | одна дата на пакет; статусы `Draft`/`Applied` |
| `CorrectionPosition` | `BatchId`, `Row`, `ChangeType`, `GroupId/GroupName`, `DayOfWeek`, `Week`, `NumberPair`, `Subject?`, `TeacherId?/TeacherName?`, `RemovedSubject?`, `RemovedTeacherId?/RemovedTeacherName?`, `RemovedNumberPair?`, `Note?`, `Status` (`Draft`/`Applied`), `HistoryId?` | позиции нумеруются с 1 в порядке создания |

### 4.2. Новые сущности

| Сущность | Поля | Правила |
|----------|------|---------|
| `BellSlot` (звонки) | `NumberPair` (1–8), `StartTime`, `EndTime` | времена пар не пересекаются, идут по возрастанию, в пределах 07:00–21:00 |
| `BigBreak` | `AfterPair` (1–8), `StartTime`, `EndTime` | не более одной большой перемены; отображается отдельной строкой дня |
| `NonWorkingDay` | `DateFrom`, `DateTo`, `Title` | одиночная дата — `DateFrom = DateTo`; `DateFrom ≤ DateTo` |
| `Practice` | `Kind` (`УП`/`ПП`), `Name` (≤100), `GroupId`, `DateFrom`, `DateTo`, `Note?` | `DateFrom ≤ DateTo`, период в пределах семестра; ≥1 преподаватель (через `PracticeTeacher`); пересечение практик одной группы — 409; `Organization` не ведётся |
| `PracticeTeacher` | `PracticeId`, `TeacherId` | join «практика — преподаватели» (многие-ко-многим); уникальность `(PracticeId, TeacherId)` |
| `PracticeDay` | `PracticeId`, `Date`, `PairCount` (1–8) | только для УП: пары выводятся в расписании дня; уникальность `(PracticeId, Date)`; CHECK 1–8 |
| `ScheduleInsert` | `Title`, `DayOfWeek`, `StartTime`, `EndTime`, `Course?` (1–4, пусто — все курсы), `IsActive` | `StartTime < EndTime`; вставка не занимает номер пары |
| `CorrectionImage` (опционально) | `BatchId`, `FilePath`, `CreatedAt` | хранит путь PNG-картинки корректировки |

### 4.3. Сидовые данные

- Вставки по умолчанию: «Разговор о важном» — понедельник 08:30–09:00; «Классный час» — четверг 12:10–13:00; для всех курсов; `IsActive = true`.
- Справочник звонков по умолчанию: 8 пар 08:30–… с большой переменой после 4-й пары (45 минут).

## 5. Общие критерии приёмки

Применяются ко всем историям раздела 6, если не указано обратное.

### 5.1. Авторизация, валидация, пагинация, UI

| Код | Критерий |
|-----|----------|
| AUTH-1 | `401 Unauthorized` если запрос без JWT токена |
| AUTH-2 | `403 Forbidden` если у пользователя нет прав на операцию |
| AUTH-3 | `404 Not Found` если ресурс не существует |
| VAL-1 | `400 Bad Request` при невалидных данных (FluentValidation) |
| VAL-2 | Сообщения об ошибках на русском языке |
| VAL-3 | `[Required]`, `[MaxLength]` на всех строковых полях DTO |
| PAG-1 | Параметры `?page={n}&pageSize={m}` (по умолчанию `page=1`, `pageSize=20`) |
| PAG-2 | Максимальный `pageSize` = 100 |
| PAG-3 | Ответ содержит `{ items, totalCount, page, pageSize, totalPages }` |
| UI-1 | **Loading**: скелетон/спиннер пока данные загружаются |
| UI-2 | **Empty**: «Нет данных» когда список пуст |
| UI-3 | **Error**: сообщение об ошибке с кнопкой «Повторить» |
| UI-4 | **Success**: тост/уведомление после успешной мутации |

### 5.2. Файлы, транзакции, конфигурация

| Код | Критерий |
|-----|----------|
| FILE-1 | Импорт принимает только `.xlsx`; файл больше 10 МБ → `400` «Файл превышает 10 МБ»; иное расширение → `400` |
| FILE-2 | Шаблоны `Расписание.xlsx` и `Корректировка.xlsx` доступны для скачивания через `GET /api/dispatcher/documents/templates` |
| FILE-3 | Имена скачиваемых файлов содержат таймстемп `dd.MM.yyyy_HH-mm-ss` (например, `Корректировка_17.09.2026_14-35-02.xlsx`) |
| TX-1 | Применение корректировки и импорт выполняются в одной транзакции: либо все изменения, либо ни одно |
| TX-2 | Повторное применение применённого пакета → `409 Conflict` |
| CFG-1 | `Semester:StartDate` и `Semester:TotalWeeks` — единый источник семестра; отдаются в `GET /api/schedule/meta`; все интерфейсы используют их, дублирование константы запрещено |
| CFG-2 | `MaxBot:BaseUrl`, `MaxBot:CorrectionChannelId`, `MaxBot:DispatchChatIds` — конфигурация (appsettings/env) |

## 6. Функциональные требования (User Stories)

### 6.1. Расписание: просмотр и редактирование

#### UC-SCH-01: Пользователь может просмотреть расписание группы

**Критерии приёмки:**
- [ ] Выбор группы; для студента по умолчанию — его группа
- [ ] Режим «День»: дата (по умолчанию — сегодня), номер недели и день недели вычисляются по дате
- [ ] Режим «Неделя»: Пн–Сб с датами и номером недели; пустые дни помечены «Нет пар»
- [ ] Режим «Семестр»: матрица «недели 1…TotalWeeks × дни Пн–Сб»; в ячейке — пары (номер, предмет, преподаватель, аудитория, метки)
- [ ] Пары отображаются с временем из справочника звонков
- [ ] Воскресенье и нерабочие даты отображаются как нерабочие; пары на них не выводятся
- [ ] UI-1, UI-2, UI-3

**API:**
- `GET /api/schedule?groupId={id}&view=day|week|semester&date=&week=` — расписание группы
- `GET /api/schedule/meta` — параметры семестра

**UI:**
- Веб: `/schedule`, мини-приложение: `/max/schedule` (режимы «День»/«Неделя»)

**Зависимости:** StudyWeek (семестр), звонки

---

#### UC-SCH-02: Пользователь может просмотреть расписание преподавателя

**Критерии приёмки:**
- [ ] Выбор преподавателя (поиск по ФИО); для преподавателя по умолчанию — он сам
- [ ] Режимы «День», «Неделя», «Семестр» — те же, что в UC-SCH-01
- [ ] В дне пары упорядочены по номеру пары; показываются группа, предмет, аудитория
- [ ] Воскресенье и нерабочие даты отображаются как нерабочие
- [ ] UI-1, UI-2, UI-3

**API:**
- `GET /api/schedule?teacherId={id}&view=day|week|semester&date=&week=`

**UI:**
- Веб: `/schedule` (переключатель «Группа/Преподаватель»), мини-приложение: `/max/schedule`

**Зависимости:** UC-SCH-01

#### UC-SCH-03: Пользователь может просмотреть календарь месяца

**Критерии приёмки:**
- [ ] Сетка месяца с количеством пар в каждом дне
- [ ] Нерабочие даты и праздники помечены цветом и подсказкой с названием
- [ ] Дни практик помечены цветом УП/ПП (см. UC-SCH-17)
- [ ] Клик по дню открывает расписание этого дня
- [ ] В боте календарь ограничен семестром (не более `TotalWeeks` недель вперёд)
- [ ] UI-1, UI-2, UI-3

**API:**
- `GET /api/schedule?groupId=|teacherId=&view=calendar&month=`

**UI:**
- Веб: `/schedule` (вид «Календарь»), бот: кнопка «Дата»

**Зависимости:** UC-SCH-01, UC-SCH-14, UC-SCH-17

#### UC-SCH-04: Система помечает изменённые пары бейджами

**Критерии приёмки:**
- [ ] Бейджи: «Добавлено», «Снято», «Замена», «Перенос», «Сам.р.»
- [ ] Источник — применённые корректировки (`ScheduleHistory`) соответствующей недели/даты
- [ ] Пары, снятые корректировкой (без «сам.р.»), не отображаются в расписании
- [ ] Пары, снятые с примечанием «сам.р.», отображаются с бейджем «Сам.р.»
- [ ] Пара, пришедшая из корректировки, отображается с соответствующим бейджем
- [ ] Бейджи видны в вебе, мини-приложении, боте и экспорте
- [ ] UI-4 при применении корректировки

**API:**
- `GET /api/schedule` (метки в составе ответа)

**UI:**
- Веб: `/schedule` (бейджи на карточках пар), мини-приложение: `/max/schedule`, бот: сообщения расписания

**Зависимости:** UC-SCH-26

- [ ] Неактивные вставки не отображаются
- [ ] AUTH-2 (изменение — только `Dispatcher`/`Admin`), VAL-1
- [ ] UI-1, UI-2, UI-3, UI-4

**API:**
- `GET /api/schedule/inserts?dayOfWeek=&course=` — список
- `POST /api/schedule/inserts`, `PUT /api/schedule/inserts/{id}`, `DELETE /api/schedule/inserts/{id}` — управление

**UI:**
- Веб: `/dispatcher/inserts` (таблица + форма)

**Зависимости:** —

#### UC-SCH-06: Диспетчер может редактировать расписание вручную

**Критерии приёмки:**
- [ ] Создание пары: группа, преподаватель (опционально), предмет, аудитория, день недели, номер пары 1–8, недели (1…`TotalWeeks`)
- [ ] Время пары берётся из справочника звонков по номеру пары
- [ ] Редактирование и удаление пары
- [ ] `400` при невалидных данных: номер пары вне 1–8, недели вне семестра, время начала ≥ времени конца

- [ ] Успешная мутация: UI-4

**API:**
- `POST /api/schedule`, `PUT /api/schedule/{id}`, `DELETE /api/schedule/{id}`
- `GET /api/schedule/{id}`

**UI:**
- Веб: `/schedule` (кнопки диспетчера), мини-приложение: `/max/dispatcher` (ручной режим)

**Зависимости:** UC-SCH-11

### 6.2. Импорт и экспорт расписания

#### UC-SCH-07: Диспетчер может импортировать расписание на семестр (превью)

**Критерии приёмки:**
- [ ] Файл `.xlsx` по шаблону `Расписание.xlsx` (`FILE-1`, `FILE-2`)
- [ ] Парсинг матрицы: группы (строки), дни недели, номера пар, предмет/аудитория/недели/преподаватель в ячейке
- [ ] Недели пар нормализуются к диапазону 1…`TotalWeeks`
- [ ] ФИО преподавателей и названия предметов нормализуются (справочник нормализации)
- [ ] Превью: список разобранных пар и полный список ошибок с адресом «Лист, строка N, столбец M: сообщение»

## 9. Нефункциональные требования

| Требование | Критерий |
|------------|----------|
| Транзакционность | применение корректировки и импорты выполняются в одной транзакции (`TX-1`) |
| Идемпотентность | повторное применение пакета не дублирует данные (`TX-2`); применение поддерживает заголовок `Idempotency-Key` |
| Отказоустойчивость уведомлений | сбой Max-уведомлений и отправки картинки не влияет на корректировку; ошибки логируются (fail-safe) |
| Асинхронность | все операции API — асинхронные, с `CancellationToken` |
| Производительность | чтение расписания семестра — один запрос с ограничением выборки; списки — с пагинацией (PAG-1…PAG-3) |
| Конфигурация | семестр, MaxBot URL, канал корректировок, каналы рассылки XLSX — конфигурация, а не константы (`CFG-1`, `CFG-2`) |
| Логирование | Serilog; неожиданные исключения — `ExceptionHandlerMiddleware`; `Result<T>` в сервисах |
| Документация API | Swagger: XML-комментарии, `[ProducesResponseType]`, примеры ответов; Postman-коллекция обновляется для каждого endpoint |
| Безопасность | пароль диспетчера хранится в виде хеша; вход диспетчера — rate limit; JWT на всех защищённых маршрутах |
| Локализация | все пользовательские сообщения и документация API — на русском языке |
| Адаптивность | веб и мини-приложение: mobile-first, поддержка тёмной темы, touch-target ≥ 44×44 px, проверка на 1366×768, ~393 px и 1920+ |
| Тестирование | модульные (xUnit + Moq + Bogus) и интеграционные (`WebApplicationFactory`) тесты на все UC; E2E (Playwright) на ключевые флоу |
