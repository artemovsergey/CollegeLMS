# MAX mini-app: продуктовый поток и UX-контракт

**Статус:** согласовано для реализации  
**Дата:** 2026-09-13

## 1. Принцип разделения каналов

MAX mini-app — основной рабочий интерфейс расписания. MAX-бот не дублирует сложные формы и таблицы:

| Канал | Ответственность |
|---|---|
| Mini-app | просмотр, поиск, избранное, настройки, история, журнал, диспетчерские формы |
| Бот | `/start`, быстрый вход, deep links, дайджест, срочные изменения, короткие действия и отправка XLSX |
| CollegeLMS API | единая авторизация, доменные правила, расписание, корректировки, история и read-модели |

Любое изменение расписания применяется только через API. Бот и mini-app не поддерживают собственные копии правил.

## 2. Пользовательские истории

### US-MAX-01: Преподаватель смотрит своё расписание

**Критерии приёмки:**

- [ ] Открытие из бота ведёт на экран «Сегодня» в контексте преподавателя.
- [ ] Доступны день, неделя и произвольная дата.
- [ ] Есть переходы на предыдущий/следующий день и неделю, а также «Сегодня».
- [ ] Текущая пара и текущая учебная неделя выделены.
- [ ] Для дня без занятий показано понятное пустое состояние.
- [ ] Ошибка загрузки содержит причину и кнопку «Повторить».

**UI:** `Главная` → `Расписание на сегодня` → `День` / `Неделя` / `Дата`.

**Зависимости:** MAX context, API расписания, календарь учебных недель.

### US-MAX-02: Студент ищет группу или преподавателя

**Критерии приёмки:**

- [ ] Поиск разделяет результаты на «Группы» и «Преподаватели».
- [ ] Результаты загружаются с debounce; пустой результат не маскируется под сетевую ошибку.
- [ ] Выбранный объект открывается на сегодняшнем расписании.
- [ ] Объект можно добавить в избранное и удалить из избранного.
- [ ] Избранное доступно с главного экрана.

**UI:** `Главная` → `Поиск` → `Результат` → `Расписание` / `Добавить в избранное`.

**Зависимости:** API поиска и favorites.

### US-MAX-03: Пользователь настраивает уведомления

**Критерии приёмки:**

- [ ] Можно включить или выключить ежедневный дайджест.
- [ ] Время выбирается от 07:30 до 08:30 с шагом 5 минут.
- [ ] Можно выбрать дни дайджеста.
- [ ] Уведомление о корректировке отправляется сразу при включённых уведомлениях.
- [ ] После сохранения показаны сохранённое время и состояние.

**UI:** `Настройки` → `Уведомления`.

**Зависимости:** API notification settings, MaxBot notifier.

### US-MAX-04: Преподаватель просматривает журнал

**Критерии приёмки:**

- [ ] Можно выбрать предмет.
- [ ] Показаны даты занятий и количество занятий на текущий момент.
- [ ] Корректировки учитываются в датах и количестве.
- [ ] UI явно различает запланированные и подтверждённо проведённые занятия, если подтверждение факта доступно.
- [ ] При отсутствии подтверждения факта интерфейс не утверждает, что занятие состоялось.

**UI:** `Журнал` → `Предмет` → `Даты и счётчик`.

**Зависимости:** отдельный API/read-model факта проведения либо явно ограниченный журнал по расписанию.

### US-MAX-05: Пользователь просматривает изменения

**Критерии приёмки:**

- [ ] Из bot notification открывается конкретная дата/пара.
- [ ] История фильтруется по периоду и контексту.
- [ ] Для операции видны тип, снятая пара, введённая пара, время, автор и примечание.
- [ ] Удалённая или устаревшая запись истории остаётся понятной и не ломает экран.

**UI:** `Изменения` → `Корректировка` → `Расписание на дату`.

**Зависимости:** ScheduleHistory и deep-link route.

### US-MAX-06: Диспетчер применяет корректировку

**Критерии приёмки:**

- [ ] Раздел диспетчера требует отдельный пароль.
- [ ] Пароль не сохраняется в localStorage и не передаётся в обычных запросах после обмена на короткую dispatcher-session.
- [ ] Доступны импорт XLSX и ручная форма.
- [ ] Превью показывает операции и ошибки по строкам.
- [ ] Подтверждение невозможно при критических ошибках.
- [ ] Повторное нажатие не применяет одну корректировку дважды.
- [ ] После успеха доступны история и XLSX результата.
- [ ] Бот может отправить сформированный XLSX в заранее разрешённую группу MAX.

**UI:** `Диспетчер` → `Пароль` → `Корректировка` → `Превью` → `Подтверждение` → `Результат`.

**Зависимости:** dispatcher-session, rate limit, idempotency, список разрешённых MAX-групп.

## 3. Навигационная структура mini-app

### Главная

- Сегодняшняя дата и учебная неделя.
- Текущая/следующая пара.
- Сводка изменений.
- Быстрые действия: «Сегодня», «Неделя», «Выбрать дату», «Поиск», «Избранное».

### Расписание

- Переключатель «День / Неделя».
- Заголовок с датой или диапазоном.
- Навигация назад/вперёд.
- Карточки занятий с предметом, временем, аудиторией, группой/преподавателем и маркером изменения.

### Избранное

- Две группы: преподаватели и группы.
- Последний выбранный контекст отображается отдельно от списка избранного.

### Изменения

- Лента корректировок с фильтрами.
- Deep link на дату и занятие.

### Настройки

- Уведомления.
- Текущий профиль/контекст.
- Справка и возврат в бот.

### Диспетчер

- Не отображается в общем меню до успешной dispatcher-сессии.
- После входа: «Новая корректировка», «История», «Последний XLSX», «Отправить в MAX».

## 4. Bot-to-app deep links

Минимальный контракт маршрутов:

```text
/miniapp?route=today
/miniapp?route=day&date=2026-09-13
/miniapp?route=week&date=2026-09-13
/miniapp?route=correction&id=<history-id>
/miniapp?route=dispatcher
```

Параметры `groupId` и `teacherId` не являются источником авторизации. Контекст пользователя и доступные объекты определяются сервером после проверки MAX context.

## 5. Состояния и ошибки

Для каждого экрана обязательны:

- loading — skeleton/spinner в структуре будущего контента;
- empty — причина отсутствия данных и следующее действие;
- error — что не загрузилось, можно ли повторить, что будет сохранено;
- offline/timeout — сохранённый последний контекст без ложного сообщения об успехе;
- success — подтверждение действия и следующий доступный шаг;
- cancel — возврат без потери ранее сохранённых данных.

Для подтверждения корректировки дополнительно нужны:

- конфликт актуальности превью;
- повторная отправка;
- частично недоступная отправка XLSX в MAX;
- успешное применение при неуспешной доставке сообщения.

## 6. Визуальное направление

Mini-app не копирует desktop-таблицу. Основной паттерн — «лента дня»: крупное время и номер пары слева, предмет как главный объект, аудитория и группа вторичной строкой, цветной маркер типа занятия/изменения.

- Использовать MAX UI как основу интерактивных примитивов.
- Сохранить спокойную плотность для быстрого сканирования одной рукой.
- Не использовать глобальные фильтры «Все группы/Все преподаватели» на первом экране.
- Главный акцент — ближайшее действие: текущая/следующая пара или новое изменение.
- Все touch targets — не менее 44 px; контраст и focus-visible обязательны.

## 7. Открытые технические решения

1. Подтвердить production-контракт подписанного MAX Bridge context.
2. Определить, где и как подтверждается факт проведённой пары для журнала.
3. Утвердить срок dispatcher-session, лимит попыток и восстановление доступа.
4. Задать whitelist MAX-групп, которым разрешена отправка XLSX.
5. Определить API-контракт единого поиска и пагинации избранного.

## 8. Принятые технические дефолты (2026-09-13)

Решения ниже зафиксированы для реализации и закрывают открытые вопросы §7 до появления
прод-контракта MAX Bridge. Любой дефолт меняется отдельным решением.

### D1. Авторизация и контекст mini-app

- Подписанный MAX Bridge context в прод-версии не подтверждён, поэтому mini-app использует
  существующий JWT-вход CollegeLMS (токен в `localStorage`, общий с веб-версией).
- `groupId`/`teacherId` в URL — **только подсказка просмотра**, никогда не источник прав.
- Личный контекст по умолчанию берётся из профиля: студент → `profile.studentData.groupId`,
  преподаватель → новый `profile.teacherData.teacherId`. В `ProfileResponse.TeacherData`
  добавляется поле `TeacherId`.
- Просмотр расписания остаётся `[AllowAnonymous]`; избранное, настройки уведомлений,
  журнал и dispatcher — `[Authorize]`.
- Deep link несёт только навигацию: `route=today|day|week|changes|correction|dispatcher`,
  `date=2026-09-13`, `id=<history-id>`.

### D2. Read-модели расписания и учебный календарь

- Единый сервис `StudyCalendar` в API: `SemesterStart = 2026-09-01`, 16 недель,
  `WeekOf(date)`, `IsInSemester(date)`, `MondayOf(date)`. Тот же календарь используется
  mini-app, вебом и ботом (сейчас дублируется в `MaxScheduleView` и `StudyWeek` бота).
- `GET /api/schedule` дополняется параметром `date`: при его наличии сервер сам вычисляет
  `week + dayOfWeek` (клиент не доверяет собственным расчётам недели).
- `GET /api/schedule/meta` (без авторизации): `{ semesterStart, totalWeeks, currentWeek,
  currentDate }` — источник истины для индикатора «текущая неделя».
- `GET /api/schedule/search?q=` возвращает единый ответ `{ groups[], teachers[], totalGroups,
  totalTeachers }` (закрывает вопрос №5). Просмотр анонимный, rate-limited.

### D3. Избранное

- Новая сущность `Favorite { UserId, TargetType: Group|Teacher, TargetId }`, с unique-индексом
  на `(UserId, TargetType, TargetId)`. Только владелец видит/удаляет свои записи.
- `GET /api/favorites`, `POST /api/favorites` (тело `{ targetType, targetId }`, идемпотентно),
  `DELETE /api/favorites/{id}`. Ответ подтягивает названия группы/ФИО преподавателя.

### D4. Настройки уведомлений

- Новая сущность `NotificationSettings { UserId (unique), Enabled, Time (TimeSpan, шаг 5 мин,
  диапазон 07:30–08:30), Days int[] }`. `GET/PUT /api/notifications/settings`.
- Валидация времени на сервере: `time >= 07:30 && time <= 08:30 && minutes % 5 == 0`.
- `GET` дополнительно возвращает вычисленный `nextNotifyAt`.
- Корректировки отправляются немедленно независимо от дайджеста; переключатель `Enabled`
  управляет только дайджестом.
- Пробел идентичности: у бота нет привязки MAX-пользователь ↔ LMS-аккаунт, поэтому единый
  источник настраиваемого времени пока недостижим. Дефолт D8:
  - mini-app управляет настройками через API (`NotificationSettings`, per LMS-user);
  - бот хранит `UserSettings.NotifyTime` (per MAX-user, по умолчанию 07:30) и применяет те же
    границы 07:30–08:30 с шагом 5 минут;
  - правило времени вынесено в константу с одинаковыми значениями в обоих проектах;
  - сквозное слияние по каналам — отдельная задача после введения привязки MAX↔LMS.

### D5. Журнал преподавателя

- `GET /api/schedule/journal?teacherId=` (JWT, владелец): выборка по субъекту и неделям,
  с учётом корректировок. Возвращает `{ subject, items: [{ date, numberPairs }], total }`.
- Факт проведения **не подтверждается** (закрывает вопрос №2): UI явно помечает
  «по расписанию», без утверждения «проведено».

### D6. Dispatcher-session

- `POST /api/dispatcher/login` с телом `{ password }`: BCrypt-сравнение с
  `DispatcherCredential` (хэш в БД, задаётся через конфигурацию/seed). При успехе выдаётся
  короткий `dispatcher-token` (JWT, TTL 30 минут, роль `Dispatcher`).
- Rate limit: 5 неудачных попыток подряд → lockout 15 минут (in-memory per IP).
- Пароль не хранится на клиенте; token сохраняется в `sessionStorage` mini-app.
- Идемпотентность `/api/schedule/correction/confirm`: обязательный заголовок
  `Idempotency-Key` (UUID); сервер хранит `{ key, resultHash, appliedAt }`, повторная отправка
  ключа возвращает сохранённый результат без переприменения.
- XLSX результата = существующий `GET /api/schedule/export?format=xlsx` для затронутой группы.

### D7. Верхнеуровневые границы бот-флоу

- `open_app` deep links получают `route=`; `groupId/teacherId` остаются как подсказка
  просмотра (deprecated, не авторитет).
- Отправка XLSX в MAX-группу: dispatcher выбирает чат из whitelist (конфиг MaxBot +
  настройка времени выполнения); если SDK MAX не поддерживает файловые вложения —
  отправляется ссылка на скачивание (проверяется в фазе C).
